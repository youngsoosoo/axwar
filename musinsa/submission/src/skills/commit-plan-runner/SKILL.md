# 커밋 플랜 실행기

이 스킬은 현재 작업트리의 변경사항을 읽고, 리뷰하기 쉬운 커밋 단위로 나눈 뒤, 사용자가 원하면 실제 커밋까지 진행한다.

## 기본 절차

1. `git status --short`와 `git diff --stat`으로 변경 범위를 확인한다.
2. `git diff --name-only`와 필요한 파일별 diff를 읽어 변경 의도를 파악한다.
3. 관련 없는 생성물이나 임시 파일을 제외한다.
4. 논리적 커밋 단위를 1개 이상 제안한다.
5. 각 커밋마다 제목, 포함 파일, 변경 요약, 검증 결과를 짧게 제시한다.
6. 사용자가 커밋 진행을 승인하면 커밋 단위별로 대상 파일만 stage하고 commit한다.
7. 각 커밋 후 `git status --short`로 남은 변경사항을 확인한다.

## 커밋 분리 기준

- 문서 정합성 수정, CLI 기능 수정, 샘플 데이터 보강, 테스트 보정은 가능한 한 분리한다.
- 한 커밋은 하나의 의도를 갖도록 구성한다.
- 같은 파일에 여러 의도가 섞여 있으면 `git add -p` 또는 더 작은 파일 단위 커밋을 검토한다.
- 리뷰어가 한 커밋만 되돌려도 의미가 유지되도록 묶는다.
- 너무 작은 오탈자성 변경은 관련 문서 커밋에 포함한다.

## 제외해야 할 파일

- `__pycache__/`, `.pytest_cache/`, `.mypy_cache/`
- 빌드 산출물, 임시 로그, OS 메타데이터
- 사용자가 명시하지 않은 `output/` 리포트 파일
- 작업과 무관한 기존 변경사항

## 커밋 진행 규칙

- `git add .`를 사용하지 않는다.
- 항상 `git add -- <파일...>` 형태로 대상 파일을 명시한다.
- 사용자가 “추천만” 요청하면 커밋하지 않는다.
- 사용자가 “진행해줘”, “커밋까지 해줘”, “추천대로 커밋해줘”라고 요청하면 제안한 단위대로 진행한다.
- 커밋 전 staging 대상 목록을 한 번 더 확인한다.
- 커밋 메시지는 기본적으로 Conventional Commits 스타일을 사용한다.
- 메시지는 한국어 설명을 허용하되 제목은 짧게 유지한다.

## 메시지 예시

```text
docs: align report output paths
feat(cli): accept optional domain argument
data: add pistachio nail trend fixture
test: update CLI verification notes
```

## 사용자에게 보고할 내용

- 추천한 커밋 개수와 각 커밋의 이유
- 실제로 stage한 파일 목록
- 생성된 커밋 해시와 제목
- 실행한 검증 명령과 결과
- 남은 변경사항이 있다면 그 이유
